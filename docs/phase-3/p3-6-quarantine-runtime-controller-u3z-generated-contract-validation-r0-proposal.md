## Why U3Z Exists

U3Y accepted the additive controller R1 source, its exact-null stage projection,
the machine-disabled Python reference, 288 generated vectors, and static
cross-language evidence. That evidence intentionally did not parse, import,
dot-source, or execute the PowerShell implementation. Python equivalence and
source-text inspection are not substitutes for bounded PowerShell behavior
evidence.

U3Z therefore introduces an additive, exact-hash-bound generated-validation
harness. It does not modify any accepted U3Y file. The current proposal only
defines the future source implementation and its later runtime gate.

## Gate H1: Source Harness

The future H1 authorization would allow exactly six additive paths: one
PowerShell harness, one materialized vector manifest, one Python generated and
static test module, one nonobservational evidence record, one implementation
package, and one evidence review.

The materialized manifest must contain exactly 288 generated-only cases, with a
one-to-one source-vector identifier and expected projection from the accepted
U3Y vector manifest. It covers all nine 32-case groups, literal-null success,
empty-string rejection, bounds and field failures, all 18 failure actions and
reasons, cross-language projection, zero retention, and closed gates.

H1 implementation may use Python only for generated fixture materialization,
the machine-disabled reference, source-text inspection, and static tests. It
may not parse or run PowerShell, inspect a runtime or machine, access external
data, or create a commit.

## Gate R1: Future Runtime-Bound Validation

Only after separate H1 source acceptance may a new proposal bind an exact
PowerShell runtime and request one generated-validation attempt. That future
attempt would be single-use, serial, generated-only, and limited to the exact

exact-null success, all nonempty failure mappings, zero cross-language
